01

Overview

HumanCare WorldWide is a medical-assistance app with two kinds of users: patients who submit a request for help (air ambulance, ground transport, hospital-to-hospital transfer, etc.), and vendor partners (TPAs, insurers, corporates) who pick up those requests and manage them to completion.

The backend — everything under backend/ in this repo — is built and working today: authentication, submitting requests, vendor case management, notifications, and file uploads. It's been tested end-to-end (via Postman/curl) and is ready for a real app to call it.

Design reference: the actual screen designs (colors, layout, copy) are shared with you directly as images — this guide covers the confirmed screen list and journey below, plus the engineering side: folder layout, the API, and what's left to build.
02

Customer journey

The confirmed screen list, in order. Two screens shown in the original design are deliberately not being built — noted below so nobody re-adds them by accident.

Part 1 — Request a service
1–2 · Splash → Welcome / Get Started
Logo screen, then "We are here for you" with Get Started / Login.
3–4 · Login / Register
Login = mobile or email + password. Register collects name, mobile, email, password, T&C consent.
5 · Home Dashboard
Greeting, "Create New Request" CTA, a preview of recent requests with status pills (Submitted / In Progress / Completed).
6–7 · Select Service → Service Details
Grid of services (Air Ambulance, Ground Ambulance, Hospitalization, Medical Escort, Mortal Remains, Home Healthcare, Teleconsultation, Other) → detail page with "Request This Service."
8–10 · Create Request — Steps 1, 2, 3
Step 1: patient details (name, age, gender, location, contact). Step 2: request details, destination, preferred date, upload documents. Step 3: additional info, special requirements, referral source.
11–12 · Review & Submit → Request Submitted
Final confirmation screen, then a success screen showing the reference number (e.g. REQ-1005).
13–14 · Quotation / Response → Accept & Confirm
Not being built. The design shows a quotation step with Accept/Decline before a case proceeds — confirmed out of scope. A submitted request goes straight to vendor handling with no quotation gate.
Part 2 — Dashboard, My Requests & Live Tracking
My Requests
Searchable/filterable list (All / Submitted / In Progress / Completed / Cancelled) → Request Details with a status stepper and a "View Tracking" link.
Live Case Tracking
Tabs: Overview (map + tracking steps), Timeline (timestamped stage log), Information (patient, medical team, aircraft/hospital, contact). Covers stages from Request Submitted through In Progress / On The Way / Service In Progress.
Live Tracking — Completed (celebration screen)
Not being built. The design includes a dedicated "Service Completed" screen with document downloads and a star rating. Skip it — when a case is done, Request Details/Tracking should just show status = Completed, no separate screen.
Heads up for whoever wires up the API: the design's tracking stepper reads "Submitted → Confirmed → In Progress → Completed," but the backend's actual stage values are submitted, scheduled, in_progress, completed, cancelled (see API Reference). There's no exact confirmed stage today — treat the design's "Confirmed" label as mapping to scheduled unless told otherwise.

Running the backend

So you have something real to point your app at while you build.

  1. 1
    Install dependencies and copy the env template: 
    cd backend
npm install
cp .env.example .env
    Fill in .env with real local database credentials (ask for these if you don't have a MySQL setup yet).
  2. 2
    Start the server: 
    npm start
    It listens on http://localhost:4000. See API Reference for what's available.
  3. 3
    On a real device or simulator, localhost won't reach your computer directly — use your machine's local network IP (e.g. http://192.168.x.x:4000) as the API base URL instead, or a tool like ngrok while testing.

API reference

Everything the app has to call. Base URL locally: http://localhost:4000. Protected routes expect Authorization: Bearer <token>, using the token from login.

Auth
MethodPathAuthWhat it does
POST/auth/register—Create a patient account: name, email, mobile, password (min 8 chars).
POST/auth/login—Patient login. identifier = email or mobile, plus password.
POST/auth/vendor/login—Vendor login — email + password only, returns a token directly (no OTP).
POST/auth/refresh—Trade a refreshToken for a new access token. Access tokens expire in 15 min — call this instead of forcing re-login.
GET/auth/meanyGet the logged-in user's own profile. Use on app launch to restore a session.
PATCH/auth/mepatientUpdate name, mobile, and/or countryCode for the Profile screen.
POST/auth/forgot-password—Send a reset code to identifier (email or mobile), if that account exists.
POST/auth/reset-password—identifier + code + newPassword → sets the new password.
Services
MethodPathAuthWhat it does
GET/services—The service grid (Air Ambulance, Ground Ambulance, etc.) with description and "We Provide" bullets, for Select Service.
GET/services/:slug—One service's detail, for Service Details. slug is also the value to send as serviceType when submitting a request.
Static reference data (not a database table) — only Air Ambulance's copy came from the shared design; the other 7 are placeholder text for the team to review/edit in backend/src/modules/services/services.data.js.
Requests — patient
MethodPathAuthWhat it does
POST/requestspatientSubmit a new request. Auto-creates a Case so vendors see it immediately.
GET/requests/mepatientList my own requests. Optional ?status= filter.
GET/requests/me/:idpatientOne request, including its case timeline and documents.
POST/requests/me/:id/documentspatientAttach a file (form-data, key file). PDF/JPG/PNG/WEBP/DOC/DOCX, max 10MB.
GET/requests/me/:id/summarypatientDownload a branded PDF summary (details + timeline) — powers "Download Summary" on Request Details.
GET/requests/track/:refguest*Track by reference number. Needs ?mobile= to match — no login needed.
Cases — vendor (mounted at /vendor/cases)
MethodPathAuthWhat it does
GET/vendorCases my organization has submitted. Optional ?status=.
GET/:idvendorOne case my organization submitted, full detail.
POST/vendorSubmit a case on behalf of someone my organization covers.
POST/:id/documentsvendorAttach a supporting file to a case I submitted.
Vendor = submit & track, not claim & manage. Insurance/Government/Corporate vendors submit on behalf of someone they cover and track status — they don't pick up or work cases themselves. That's done by HumanCare's own Operations team in Bitrix24 (see Roadmap); status updates flow back into this system from there, not from a vendor-side "update stage" action.
Notifications
MethodPathAuthWhat it does
GET/notificationsanyMy notifications. Optional ?unreadOnly=true.
POST/notifications/:id/readanyMark one as read.
POST/notifications/read-allanyMark everything read.
* Guest = deliberately no login — patients tracking a request without an account, gated by matching the request's mobile number instead of a token.

Roadmap

What's shipped, what's next, and what's intentionally on hold.

Backend core (auth, requests, cases, notifications, file upload) in progress
Password login, token refresh, profile, and password reset all work for patients; vendor password login works too. Submitting a request auto-opens a case; vendors (Insurance/Government/Corporate) submit and track cases on behalf of who they cover; patients get notified; documents can be attached by either side. Not every planned auth option is built yet.
Version control & team repo done
Git is set up locally; next is pushing to GitHub and adding you as a collaborator.
Build the React Native app next up
The single biggest remaining piece — see Architecture. Everything in API Reference is ready and waiting, and the confirmed screen list is in Customer Journey.
Deploy the backend online planned
Currently only reachable at localhost:4000 — needs hosting (e.g. Hostinger) before it's reachable from a real device on a different network.
Bitrix24 CRM sync planned — scoped
Two one-way flows, not one complex two-way sync: (1) new request/case → auto-creates a lead in Bitrix24, so Operations works entirely in Bitrix24 as they do today; (2) a Bitrix24 automation rule calls a webhook on our backend whenever Operations moves a lead's stage, which updates that case's status here and notifies the patient/vendor. Needs Bitrix24 account access + API credentials before it can be built.
Google / Apple sign-in on hold
Needs a Google Cloud project and a paid Apple Developer account ($99/yr) registered to the company — a business decision, not a coding one.
Admin dashboard (website) planned, not started
A separate internal website (not the patient/vendor app) for HumanCare staff — single admin login, no permission tiers needed for now (just 1–2 trusted staff). Scope: add new vendor companies + their logins (currently done by hand via a script), a god-view across every vendor's cases, an editor for the Services list (currently a code file only a developer can change), and patient account lookup for support. Deliberately deferred — nothing urgently needs it while there's only one vendor; revisit once real vendor partners start onboarding.
